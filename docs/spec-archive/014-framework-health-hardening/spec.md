# Feature Specification: Framework Health Hardening

**Feature Branch**: `feat/014-framework-health-hardening`

**Created**: 2026-08-28

**Status**: In progress

**Input**: User description: "Write Spec Kit specifications for the outstanding
repository hygiene, historical browser evidence, maintainability, release
automation, and toolchain work, then execute them."

## User Scenarios & Testing

### User Story 1 - Start from an unambiguous repository state (Priority: P1)

A maintainer working from Windows or another platform sees the same clean
working tree, can distinguish real edits from line-ending conversion, and does
not have to route around obsolete merged branches or worktrees.

**Why this priority**: False dirty state and obsolete worktrees undermine every
later validation and release decision.

**Independent Test**: Create or inspect representative worktrees using the
repository's declared text policy, verify that tracked source remains clean,
and confirm every retired branch is already contained by `main` before removal.

**Acceptance Scenarios**:

1. **Given** a clean checkout on Windows, **When** tracked source is inspected,
   **Then** line-ending conversion alone does not report source modifications.
2. **Given** the duplicate typography worktree and its branch, **When** their
   changes are compared while ignoring end-of-line whitespace, **Then** no
   semantic diff exists before they are retired.
3. **Given** a local or remote historical branch, **When** it is selected for
   retirement, **Then** it is already merged into `main` and is neither `main`
   nor the active Spec 014 branch.

---

### User Story 2 - Trust completed specification evidence (Priority: P2)

A maintainer reading the specification archive can tell whether every accepted
gate passed, was explicitly waived, or remains open without interpreting an
unchecked task that contradicts the package disposition.

**Why this priority**: Archived packages are the durable evidence for public
contracts and must not look half-finished after acceptance.

**Independent Test**: Review the previously unavailable Pattern Atlas and
representative component states in the requested in-app browser, then reconcile
the two historical task records and review evidence with the observed result.

**Acceptance Scenarios**:

1. **Given** the four built-in tiers, **When** representative Pattern Atlas
   states are reviewed at desktop and constrained widths, **Then** composition,
   overflow, console, focus, and directional behavior meet the accepted
   contracts.
2. **Given** an archived acceptance task, **When** its disposition is read,
   **Then** it is marked completed or explicitly waived rather than left as an
   unexplained open checkbox.

---

### User Story 3 - Change cohesive framework areas safely (Priority: P3)

A contributor can locate and change one component family or validation domain
without editing a multi-thousand-line mixed-responsibility owner, while the
generated public package and behavioral coverage remain unchanged.

**Why this priority**: The present implementation is correct but concentrated;
smaller owners reduce review cost and accidental cross-component regressions.

**Independent Test**: Extract cohesive modules from each identified hotspot,
rebuild twice, and compare public generated output and the complete validation
results with the pre-refactor baseline.

**Acceptance Scenarios**:

1. **Given** component CSS assembly, **When** a cohesive legacy family is
   extracted, **Then** output order and generated bytes remain unchanged.
2. **Given** static build validation, **When** assertion groups are extracted,
   **Then** the same public contracts are asserted with the same failure
   semantics.
3. **Given** browser behavior validation, **When** scenario groups or helpers
   are extracted, **Then** the same routes, interactions, and assertions run.

---

### User Story 4 - Publish repeatably without interactive credentials (Priority: P4)

A package maintainer can release an unused version from an exact commit through
the trusted workflow and receive registry, clean-install, tag, checksum, and
GitHub release evidence without a long-lived publish token or manual browser
authentication.

**Why this priority**: Trusted publishing is established; completing the
surrounding checks removes the remaining error-prone manual release steps.

**Independent Test**: Exercise all non-publishing release checks locally and in
CI, then use the workflow for the next package version and verify that npm and
GitHub expose the same tested artifact and source commit.

**Acceptance Scenarios**:

1. **Given** an already-published version or a ref/version mismatch, **When**
   release is requested, **Then** publication stops before the registry changes.
2. **Given** a valid unused version, **When** the trusted workflow runs, **Then**
   it publishes without a stored npm write token and verifies an exact clean
   registry installation.
3. **Given** successful registry verification, **When** closeout completes,
   **Then** the same commit is tagged and its package tarball is attached to a
   GitHub release with recorded checksums.

---

### User Story 5 - Work within a declared supported toolchain (Priority: P5)

A maintainer and downstream build consumer can see the supported Node range and
reproduce the repository with the declared package manager while current stable
major development tools are either adopted successfully or explicitly deferred
with evidence.

**Why this priority**: Silent runtime assumptions and opportunistic major
upgrades create avoidable downstream and release risk.

**Independent Test**: Install and run the complete gates on every declared CI
runtime, validate the packaged build API in a clean consumer, and record the
disposition of each available major upgrade.

**Acceptance Scenarios**:

1. **Given** an unsupported runtime, **When** dependencies are installed,
   **Then** package metadata communicates that the runtime is outside support.
2. **Given** each supported CI runtime, **When** the complete non-screenshot and
   release gates run, **Then** they pass consistently.
3. **Given** a current stable major tool upgrade, **When** it is evaluated,
   **Then** it is landed only if build, demo, browser, package, and release
   contracts remain green; otherwise its concrete blocker is recorded.

### Edge Cases

- A worktree that contains semantic edits must be preserved even if its branch
  is merged.
- Branch cleanup must not remove `main`, the active spec branch, unmerged work,
  tags, or user-owned temporary directories.
- Browser review must use the requested in-app browser; another browser is not
  silently substituted.
- Module extraction must not reorder CSS, rename public selectors, change
  assertion messages relied on during diagnosis, or hand-edit generated files.
- Registry publication is immutable; every preflight must complete before the
  publish command.
- The private repository cannot provide npm public provenance under the current
  registry limitation; release evidence must not claim that it does.
- A stable major that fails the existing contract is documented and deferred
  rather than forced into the release.

## Requirements

### Functional Requirements

- **FR-001**: The repository MUST declare deterministic text-file line endings
  for tracked source, documentation, configuration, and workflow files.
- **FR-002**: The duplicate typography worktree and branch MUST be retired only
  after a semantic-diff check proves its reported modifications are line-ending
  artifacts and its commit is contained by `main`.
- **FR-003**: Historical local and remote branches MAY be retired only when they
  are merged into `main`; protected, active, or unmerged refs MUST remain.
- **FR-004**: The two open Spec 001 browser tasks MUST receive an actual in-app
  browser result or an explicit owner-approved waiver recorded consistently in
  both the task list and review.
- **FR-005**: The Pattern Atlas review MUST cover representative desktop and
  constrained states, all four built-in tiers, console errors, overflow,
  keyboard focus, and directional behavior where applicable.
- **FR-006**: Each identified code hotspot MUST yield at least one cohesive
  focused module, and each original owner MUST decrease by at least 25 percent
  without creating a new file larger than the reduced owner.
- **FR-007**: Refactoring MUST preserve generated CSS/JSON bytes, public exports,
  demo routes, assertion coverage, and browser behavior unless a documented
  test-only diagnostic improvement is required.
- **FR-008**: Release preflight MUST reject an already-published version and a
  release candidate whose version, source ref, or working package contents do
  not agree.
- **FR-009**: Publication MUST continue to use the existing npm trusted
  publisher and MUST NOT introduce a stored npm write token.
- **FR-010**: Release closeout MUST verify the exact registry artifact in an
  empty consumer and create a matching source tag, checksum record, package
  tarball attachment, and GitHub release.
- **FR-011**: Package metadata and contributor documentation MUST declare the
  supported Node and package-manager contract, and CI MUST exercise each
  supported release runtime represented by the contract.
- **FR-012**: Stable TypeScript and Vite major upgrades available at planning
  time MUST be evaluated against the complete package and demo contracts; only
  green upgrades may be committed.
- **FR-013**: The public BF selectors, four-tier surfaces, generated font
  metrics, package export map, and downstream import forms MUST not change as a
  side effect of this maintenance package.
- **FR-014**: `npm test`, `npm run qa:components`, package dry-run inspection,
  clean consumer installation, and the relevant browser review MUST pass before
  release.

## Success Criteria

### Measurable Outcomes

- **SC-001**: A fresh Windows checkout and a second worktree report zero
  line-ending-only modifications after the declared text policy is applied.
- **SC-002**: Zero unmerged or protected branches are deleted, and every retired
  ref has a recorded successful ancestry check against `main`.
- **SC-003**: All 13 archived packages contain zero unexplained unchecked tasks;
  any waived task is labelled with its durable disposition.
- **SC-004**: Each of the three identified hotspot owners is at least 25 percent
  shorter, and the rebuilt public generated CSS, JSON and font artifact hashes
  match the pre-refactor hashes before dependency upgrades; compiled internal
  module bytes may change while their public exports and behavior remain stable.
- **SC-005**: The release workflow rejects two negative fixtures—an existing
  registry version and a version/ref mismatch—before any publish step.
- **SC-006**: The released artifact passes all documented root, build, CSS,
  token, surface, preset, and four-tier import checks in an empty directory.
- **SC-007**: CI and local closeout complete with zero security advisories, zero
  baseline failures, zero overflow failures, and zero missing component
  coverage.
- **SC-008**: The npm version, Git tag, GitHub release source commit, attached
  tarball checksum, and clean-install version all agree exactly.

## Assumptions

- The user's instruction to execute this package is explicit approval to
  discard the verified line-ending-only duplicate worktree state and delete
  merged historical branches after guard checks.
- Candidate product specifications in `docs/specs.md` remain evidence-gated and
  outside this maintenance package.
- Public runtime behavior does not need a new primitive, selector, tier, or
  compatibility alias.
- Node 22 and Node 24 are the relevant maintained release runtimes; research
  will determine the exact minimum declared version from official requirements.
- A maintenance release is appropriate because package metadata and release
  behavior change even when generated design-system bytes do not.
